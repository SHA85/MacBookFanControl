Technical Documentation · Version 1.0 (build 1)

MacBookFan for macOS

A menu bar fan controller and thermal monitor for Apple Silicon Macs. It reads AppleSMC and IOHID temperature sensors, and drives the fans in Automatic, Constant RPM or Sensor-based mode through a small root helper.

macOS 14+Apple Silicon (M1 – M5)Swift · SwiftUI + AppKitIOKit · XPC · SMAppServiceNo third-party dependenciesUpdated 23 Nov 2026

01Overview

What the app is, what it does, and the numbers that matter.

MacBookFan (shown in the UI as macbook_fan) is a menu bar–only app (LSUIElement = YES, no Dock icon). Its status item shows the CPU temperature and the first fan's speed, for example 41°C 2,317 rpm. Clicking it opens a popover with fan controls and key temperatures; a separate Details window lists every sensor.

Every 2 seconds the app:

  1. Reads all temperature sensors (AppleSMC keys + IOHID die sensors) and the current RPM of each fan.
  2. Computes a target RPM per fan from its mode and settings.
  3. If fan control is enabled, sends the target to the root helper over XPC; the helper writes it to the SMC.

The app itself always runs as the logged-in user. Writing to the SMC needs root, so those writes go through a launchd daemon that is the same executable started with --helper. When the app quits or crashes, every fan goes back to macOS control.

02Architecture

Two processes from one binary: the user-level app and a root helper.

Why a separate helper?

  • SMC writes (kSMCWriteKey) need root. Reads do not.
  • macOS does not show menu bar items for apps running as root, so running the whole app with sudo would hide the UI.
  • The helper is registered with SMAppService.daemon. The user approves it once in System Settings → General → Login Items & Extensions; no password prompt after that.

06Temperature sensors

How raw readings become the rows shown in the UI (getFormattedSensors()).

IOHID die sensors

CPU, GPU and SSD temperatures on Apple Silicon come from the private IOHIDEventSystem, declared with @_silgen_name. The client matches PrimaryUsagePage 0xff00 / PrimaryUsage 5 and reads event type 15 (temperature) from each service. Values outside 10–125 °C are dropped.

07Fan control modes

Per-fan settings and how a target RPM is chosen.

ModeTargetSMC effect
AutomaticnoneF#Md = 0; Ftst = 0 once every fan is automatic. macOS (thermalmonitord) controls the fan.
Constant RPMclamp(constantRPM, min, max)Forced mode + F#Tg. UI slider snaps to 100 RPM; presets Min / 33% / 66% / Max.
Sensor-basedLinear curve on a chosen sensorForced mode + F#Tg, or stop (target 0) below the start temperature.

Sensor-based curve

if stopBelowStart and temp < (wasRunning ? start − 2 : start)  →  0 (fan off)
if temp ≤ start                                            →  minRPM
if temp ≥ max                                              →  maxRPM
else                                                       →  minRPM + (temp − start) / max(1, max − start) × (maxRPM − minRPM)

Safety rules in the store

  • constantRPM is always clamped to the fan's own min/max.
  • If “Full speed at” ≤ “Start”, it is moved to start + 1.
  • If the chosen sensor stops reporting, the fan runs at max RPM (fail safe), not min.
  • A sensor ID this Mac has never reported is replaced with the best available: CPU_AVG → any CPU → GPU → power sensor → first sensor.

Forced mode on Apple Silicon

  1. Write F#Md = 1 (falls back to lowercase F#md if that key exists instead).
  2. If refused and Ftst exists: write Ftst = 1, then retry the mode write up to 10 times, 100 ms apart. thermalmonitord holds the fan until Ftst is set.
  3. Write the clamped target to F#Tg (encoded per the key's type).
  4. To stop a fan, the target is 0. If the SMC refuses that, the fan is handed back to macOS, which keeps it off while the Mac is cool.

08Control loop

FanControlStore — the single source of truth for UI and fan writes.

A Timer fires every 2 s on the main run loop in .common mode, so it keeps running while the popover or a menu is being tracked. Each tick():

  1. Refreshes the helper status from SMAppService.
  2. Reads all sensors; publishes them only if they changed.
  3. Reads each fan's current RPM (F#Ac).
  4. Resolves any never-seen sensor selection; saves settings if that changed something.
  5. commit(): recomputes each fan's target, publishes only real changes, then pushToSMC().

Writes

  • Nothing is written unless the helper status is .enabled.
  • Writes run on a serial queue (macbook_fan.smc.write) because the XPC calls are synchronous.
  • Only one write per fan is in flight at a time (pendingWrites); a fan with a write pending is skipped that tick.
  • Target ≤ 0 → stopFan; otherwise setFanSpeed. The result updates lastWriteFailed and the popover error banner.
  • Switching a fan to Automatic, or pressing Auto in the popover, calls setAutomatic; Ftst is released only when no fan is manual any more.

XPC interface

@objc protocol FanHelperProtocol {
    func setFanSpeed(fanIndex: Int, rpm: Double, reply: (Bool) -> Void)
    func stopFan(fanIndex: Int, reply: (Bool) -> Void)
    func setAutomatic(fanIndex: Int, releaseTestMode: Bool, reply: (Bool) -> Void)
}

The app connects with NSXPCConnection(machServiceName: "macbook_fan.helper", options: .privileged) and uses synchronousRemoteObjectProxyWithErrorHandler. A dropped connection is cleared in the invalidation handler and recreated on the next call.

Helper lifetime

  1. launchd starts it when the app first connects. It exits unless it is root (geteuid() == 0).
  2. It builds a client requirement from its own signature and refuses to run if it has no Team ID.
  3. Every call is validated (0 ≤ fanIndex < FNum, finite RPM) and serialised on one queue.
  4. When the client count drops to 0: all fans → automatic (Ftst released on the last), then exit after 5 s unless a client reconnects.

10Single instance

Two copies would fight over the fan target every tick. The newest copy wins.

  1. On launch, register for the Darwin notification digit.macbook_fan.instance-launched, then post it.
  2. Every running copy that receives it scans processes with sysctl(KERN_PROC_ALL) for the same process name (skipping root processes, which are the helper). If a newer one exists, it quits normally, which hands the fans back.
  3. After 2 s the new copy sends SIGTERM to any older copy that didn't quit.

“Newer” = later start time, then higher PID. This also makes re-running from Xcode replace the previous build cleanly.

14Build & install

From source to a drag-to-install DMG.

# from the MacBookFan folder
./scripts/build-dmg.sh
  1. Clean Release build with xcodebuild into build/DerivedData (-allowProvisioningUpdates).
  2. Checks that macbook_fan.helper.plist is in the app, that its BundleProgram exists, and that codesign --verify --deep --strict passes.
  3. Prints version, build, bundle ID, minimum macOS and architectures.
  4. Stages the app, an Applications link and a bilingual “README - How to Install.txt”.
  5. Creates dist/MacBookFan-<version>.dmg (HFS+, UDZO, zlib 9) and a .sha256 file.

First run

  1. Drag the app to Applications and open it. If macOS blocks it, use System Settings → Privacy & Security → Open Anyway.
  2. Click the menu bar item → Enable Fan Control.
  3. Turn the app on in System Settings → General → Login Items & Extensions → Allow in the Background.
  4. Pick a mode for each fan. Do not run the app with sudo.

Publishing a GitHub release is described in Notes.md.

16Performance

Where the work goes.

  • Startup: one SMC call per key to find temperature keys (the full key scan), plus a single ioreg call for the SSD model name.
  • Every 2 s: one IOHID client and service sweep, a handful of SMC reads, and a fan RPM read per fan.
  • UI: @Published values are replaced only when they actually change, so SwiftUI doesn't redraw the popover every tick.
  • Writes: in manual modes, each tick sends the target for every manual fan over XPC (one in flight per fan); the helper re-asserts forced mode before each target write.
  • Helper: exists only while the app is connected; exits 5 s after the last client leaves.

17Security & safety

What protects the root helper and the hardware.

  • Client check: the helper only accepts XPC clients matching identifier "<its own id>" and anchor apple generic and certificate leaf[subject.OU] = "<its own team>".
  • Small surface: three methods only — set speed, stop, automatic. No arbitrary SMC key writes are exposed.
  • Input validation: fan index must exist; RPM must be finite and is clamped to the fan's min/max.
  • Fail safe: missing sensor → full speed; app quit/crash → all fans automatic.
  • Least privilege: UI and sensor reads run as the user; only writes run as root.
  • No network, no data collection. Settings stay in local UserDefaults.
Hardware note Manual modes override macOS thermal management. Keep speeds within the fan's reported range and watch temperatures under heavy load.

18Known limitations

  • Distribution: signed with an Apple Development certificate and not notarized. For other Macs, a Developer ID certificate and notarization are needed.
  • Private APIs: IOHIDEventSystem functions are undeclared SPI; a future macOS could change them. Not eligible for the Mac App Store (also because the sandbox is off).
  • Apple Silicon focus: the binary is universal, but the IOHID sensor names and Ftst unlock are Apple Silicon specific; Intel Macs are untested.
  • Per-core temperatures are an ordered approximation (see section 06).
  • Menu bar label and stat tile show the first fan only; every fan still gets its own control card.
  • Fanless Macs (FNum = 0) still show one fan card with no readings.
  • Fan names assume fan 0 is left and fan 1 is right on two-fan Macs.
  • Naming: project MacBookFan, product MacbookFan, UI text and identifiers macbook_fan.
